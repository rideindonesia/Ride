---
name: Trip-vertical billing distance
description: goride/gocar/gosend/goshop/gofood are billed on pickup→destination distance with no free km, unlike the on-site services.
---
The Gojek-style verticals (goride, gocar, gosend, goshop, gofood) are "trip" services: the call fee is charged over the pickup→destination distance. The original on-site services (bengkel/elektronik/cuci/barber/inspeksi) charge over the mitra→pickup distance with a free-km allowance.

**ZONE-BASED motor pricing (2026 redesign):** the four motor/kurir verticals `goride/gosend/goshop/gofood` (set `MOTOR_TRIP_SERVICES`, `isMotorTripService()`) are billed PER ZONE, NOT `freeKm:0`. Fare = `motor_zone{z}_base + max(0, distKm - motor_free_km)*motor_zone{z}_per_km` where the base is a MINIMUM covering the first `motor_free_km` (default 4) km. Zone (1/2/3) is derived from the PICKUP coords via `zoneFromCoords(lat,lng)` — a geographic-constant function (Jabodetabek→Z2, Jawa/Bali/Sumatra→Z1, else Z3) duplicated verbatim in `pricing.ts` + `mitra.ts`; tarif VALUES live in `system_settings` (`motor_zone{1,2,3}_base/_per_km`, `motor_free_km`). Only `gocar` remains a flat `CALL_FEE_CONFIG` entry (`call_fee_gocar_base/_per_km`, freeKm 0). `calcBiayaPanggilan(svc, distKm, zone=3)` takes zone as 3rd arg — every caller (OrderTrip, OrderFood, DashboardMitra incoming-fare) must pass `zoneFromCoords(pickupLat,pickupLng)`.

**Commission split:** trip services (all 5, via `isTripService`) pay `platform_fee_pct_trip` (default 5%); on-site jasa panggilan pay `platform_fee_pct` (default 15%). `platformFee = round(callFee * pct/100) + biaya_layanan_admin`. Backend picks the key in the payment-data route; `DashboardMitra.tsx` mitra-facing fee display must also branch on `isTripService(o.serviceType)` (NOT a single hardcoded 15%). `goshop` enforces a `belanja_max_talangan` cap server-side (400 if sparepart exceeds).

**Seed gotcha:** `/seed/admin` upserts settings with `onConflictDoNothing()`, so it inserts NEW keys on existing DBs but will NOT overwrite a changed default (e.g. old `call_fee_gocar_base`); reconcile changed defaults with a manual UPDATE on already-seeded dev DBs. Also restart the api-server workflow after editing seed.ts (esbuild dev bundle is not hot-reloaded for the seed array). **Towing is NOT in `TRIP_SERVICES`** — it is billed as on-site (mitra→pickup) with its own free km, even though it collects a destination and DISPLAYS a pickup→dest "jarak derek" in DashboardMitra. That display-vs-billing mismatch for towing is pre-existing; do not "fix" it by moving towing into TRIP_SERVICES without an explicit product decision (it would change towing prices).

**Why:** A/B transport & courier fares must reflect the passenger/parcel journey, not how far the mitra travels to reach pickup. Getting this wrong makes the mitra's pre-accept fee preview disagree with the backend-computed fare.

**How to apply:** Anywhere a call fee is computed for a trip vertical, use the pickup→destination distance (`tripDistanceKm` on the order, or haversine(pickup,dest)) — NOT mitra→pickup. `isTripService()` / `TRIP_SERVICES` in `ride-splash/src/utils/pricing.ts` and the matching set in `api-server/src/routes/mitra.ts` + `pengguna.ts` are the single source of truth; keep all three in sync. The mitra→pickup distance is only for arrival ETA. Any UI that deep-links to an order (e.g. active-order resume card) must derive the route from `serviceType`, never hardcode `/order/bengkel`.

**Ojol umbrella consolidation (mitra side):** mitra register as a single `serviceType="ojol"` (Gojek-style) and receive/accept ALL FOUR trip order types: `goride/gosend/goshop/gofood`. The separate gosend/goshop/gofood mitra registration options were removed; `gocar` stays a separate passenger-only registration. The pengguna (customer) side is unchanged — customers still order goride/gosend/goshop/gofood/gocar as distinct services. Matching is legacy-safe via two lists kept in sync in `pengguna.ts` + `mitra.ts`: `OJOL_ORDER_TYPES=[goride,gosend,goshop,gofood]` and `OJOL_CAPABLE_MITRA=[ojol,goride,gosend,goshop,gofood]` (old dedicated mitra still work). Three matching sites use them (broadcast, mitra-online, incoming-orders) PLUS a server-side capability guard on `PATCH /mitra/orders/:id/accept` (403 on mismatch) — the guard is essential because incoming-orders only *hides* mismatched orders; without it an ojol mitra could accept a gocar order via direct API. `socket.ts` identify joins all four `service:*` rooms for ojol-capable mitra so they get `order:new` + pending-cancel events. **Why:** gocar must stay passenger-only and service-capability must be enforced server-side, not just in UI. **Keep in sync:** the OJOL lists + isTripService/TRIP_SERVICES + SERVICE_CONFIG (`DashboardMitra.tsx`, needs an `ojol` entry for the profile label) all track the same vertical set.

**Anti-double-order (all services, incl. ojol cross-vertical):** the accept endpoint (`PATCH /mitra/orders/:id/accept`) is the ONLY path that assigns `mitraId`. Double-order prevention is service-agnostic (checks `mitraId` + active statuses `["accepted","menuju","tiba","pengerjaan"]`), so an ojol mitra who accepts a goride order automatically cannot accept gosend/goshop/gofood. The SELECT `existingActive` pre-check gives a friendly 409 but is NOT atomic; the real guarantee is a `NOT EXISTS (... o2.mitra_id = ... AND o2.status IN (...))` condition inside the accept UPDATE's WHERE (closes the two-simultaneous-accept race). **Critical:** when that UPDATE matches zero rows the handler MUST return 409 — the original code fell through to `res.json({ ok:true })`, silently reporting success for an order already taken by another mitra. Any new order-assignment path must replicate both the atomic NOT EXISTS and the zero-row 409.

**Road-distance (OSRM), not straight-line:** trip distance follows actual roads via the free public OSRM server (`router.project-osrm.org/route/v1/driving/{lng},{lat};{lng},{lat}`). The order's persisted `tripDistanceKm` is computed at order-creation in `pengguna.ts` (`roadDistanceKm()`, falls back to haversine on failure/timeout), so the mitra fare preview and final fare both inherit road distance from that stored value. Both trip order pages — `OrderTrip.tsx` (goride/gocar/gosend/goshop) and `OrderFood.tsx` (gofood; pickup = merchant, dest = user) — fetch the same OSRM route for the live estimate + draw the blue route polyline; they prefer OSRM distance and only fall back to haversine while the route is still loading/unavailable, clearing any stale polyline on failure. **Why:** haversine underestimates real travel distance (straight line ≪ road), making fares too cheap. **Keep in sync:** if you change the distance source on one side (frontend estimate vs backend persisted), change both or the estimate will disagree with the charged fare.
